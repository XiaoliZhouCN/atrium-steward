## 1. 工作区定义

**Manager 工作区**是个人数字工作区的代码、内容与资产集合。`Manager/` 存放长期维护的基础设施与工具，`Projects/` 存放独立项目，两者物理隔离。

### 1.1 物理布局（实测）

```text
D:/Repositories/
├── Manager/                     # 工作区核心
│   ├── AtriumSteward/           # 常驻主控 + 工作区级文档
│   ├── AtriumCppTools/          # C++ 重型工具
│   ├── AtriumPyTools/           # Python 轻量工具与脚本
│   ├── AtriumNote/              # 内容资产仓库
│   ├── launchers/               # 启动脚本（当前为空，无 git）
│   └── .venv/                   # 唯一共享虚拟环境
├── Projects/                    # 独立项目（3D_RPG_Unity / ChestNut_Village /
│                                #   ChestTarot / ChromaCMS / NexusRenderer /
│                                #   OpenGLRenderer / ShaderLearning）
├── Storage/                     # 跨仓库数据（data / outputs / cache / shared_assets）
└── DeepseekHarness/             # 外部工具链，不受本规范约束
```

**唯一虚拟环境**：`Manager/.venv`。各仓库不得创建独立虚拟环境。

### 1.2 目录红线

| 编号 | 规则 |
| :-- | :-- |
| L1 | `Manager/` 与 `Projects/` 必须物理隔离 |
| L2 | `Projects/` 下不得创建与 `Manager/` 同名的仓库 |
| L3 | 只允许 `Manager/.venv` 一个虚拟环境 |
| L4 | `Storage/` 只作为数据落点，不作为代码仓库 |
| L5 | `Manager/` 下仓库数量保持稳定，原则上不超过 5 个 |

## 2. 设计原则

1. **关注点分离**：宿主、工具、内容三层不互相越界（见 §3）。
2. **约定优于配置**：统一目录与命名，减少额外决策。
3. **离线优先**：工作区默认按离线可运行设计，不以联网能力为前提。
4. **契约先行**：工具接入宿主前先定义协议，不写源码直连。
5. **简单优先**：优先结构清晰、人工可维护的方案，避免过度工程化。
6. **内容与代码分离**：应用代码与内容资产不得混放。

## 3. 仓库职责矩阵

| 仓库 | 定位 | 内部规范来源 |
| :-- | :-- | :-- |
| `AtriumSteward` | 常驻主控：工具生命周期、工作区上下文、轻量入口面板、工作区级文档 | `AtriumSteward/README.md` |
| `AtriumCppTools` | C++ 重型工具集合，独立进程、由宿主托管生命周期 | `AtriumCppTools/README.md`（权威） |
| `AtriumPyTools` | Python 轻量工具与脚本，无 UI 框架、无宿主逻辑 | 各工具 `docs/ARCHITECTURE_DESIGN.md` |
| `AtriumNote` | 内容资产仓库：Markdown、附件、索引产物 | `AtriumNote/README.md` |
| `Projects/*` | 独立项目，不依赖 `Manager/`，也不被 `Manager/` 反向依赖 | 各项目自身 |

**跨仓库红线**：

| 编号 | 规则 |
| :-- | :-- |
| R1 | `AtriumCppTools` 与 `AtriumSteward` 只通过契约交互，禁止 `#include` / link 对方源码 |
| R2 | `AtriumPyTools` 严禁引入 UI 框架，严禁返回 UI 控件 |
| R3 | `AtriumSteward/core/` 为纯逻辑层，严禁依赖 Qt / WebView |
| R4 | 任何仓库不得把 `Projects/` 下的项目变成构建期依赖 |
| R5 | 工具接入宿主必须经过注册表与协议，禁止隐式源码直连 |
| R6 | 状态类数据只允许写入 `Storage/cache/<tool_id>/`，不得写入仓库目录 |
| R7 | 代码组织必须保持可人工维护，禁止无必要的复杂封装 |

## 4. 跨仓库协作

- **不使用 Git Submodule**。跨仓库引用走相对路径、环境变量或契约文件。
- **允许参考与搬运，禁止依赖**：可参考其他仓库的架构决策，可把某段能力复制进来独立演化（需记录来源），但不得 `link` / `#include` 外部仓库的 target 或源码。
- **工具与宿主**：工具必须能在没有宿主的环境下独立完成全部功能；接入宿主只是增量能力（可被唤醒、观测、统一关闭）。
- **共享契约不共享实现**：接口与实现同步进入共享层，没有第二个消费者的接口不得提前提升为公共契约。

## 5. 文档规范

### 5.1 文档分级（唯一权威链）

```text
第 1 级  本文件                                 工作区级、跨仓库约束
第 2 级  <repo>/README.md                        仓库级规范与边界
第 3 级  <repo>/Docs/ARCHITECTURE_DESIGN.md      架构设计与契约
第 4 级  <dir>/AGENTS.md                         Agent 协作边界（子目录优先）
```

**冲突时以上级为准。** 同一事实只允许在第 1 级或第 2 级出现一次，下级只做链接引用，不复制条文。

### 5.2 文档红线

| 编号 | 规则 |
| :-- | :-- |
| D1 | 不得出现两份内容重叠的"权威"文档；版本号不进入文件名 |
| D2 | 历史版本交给 git，工作树内不建 `stored/` 之类的归档目录 |
| D3 | 禁止空 README、禁止只有一个标题的占位文档 |
| D4 | 所有文本文件统一 UTF-8（无 BOM） |
| D5 | 目录大小写统一为 `Docs/`（子目录内如需保持小写 `docs/`，必须在该仓库 `README.md` 中显式声明） |
| D6 | 设计变更必须同步更新对应文档，不允许只改代码 |

### 5.3 各仓库最小文档要求

每个 `Manager/` 下仓库必须有：

1. `README.md`：定位、当前状态、目录结构、安装与运行、已知限制。
2. 一份架构文档：`Docs/ARCHITECTURE_DESIGN.md`。
3. 有 Agent 协作需求时，根级 `AGENTS.md`。

## 6. 人机协作（Agent）规范

### 6.1 角色与权限

| 档位 | 角色名 | 职责 | 权限 |
| :-- | :-- | :-- | :-- |
| **建设档** | 架构师 Agent | 目录规划、接口骨架、架构文档与必要函数框架 | 允许建分支、提交、推送；不允许开 PR |
| **掌籍档** | 测试 + 文档管理 Agent | 测试补充、验证执行、文档同步、内容整理与分流 | 仅允许修改本地文件 |
| **视务档** | 模块开发 Agent | 具体模块功能实现、工具脚本与呈现 | 仅允许修改本地文件 |

档位列与角色名为同一权限的两种引法：**新文档请只用档位名**，角色名为历史引用保留。

档位的完整定义（作用域、叠加、降级、禁止事项）与各仓库角色映射见 [`AGENT_ROLES.md`](AGENT_ROLES.md)；该文档是本文 §6 的展开，不改变以上权限结论。

### 6.2 规则文件组织

- 根级 `AGENTS.md` 负责仓库级边界、角色、权限与通用禁令。
- 子目录 `AGENTS.md` 只补充局部特殊规则，默认继承上层约束。
- 较长说明（模块清单、依赖边界、适配契约）放 `Docs/`，由 `AGENTS.md` 链接引用。
- 子仓库 `AGENTS.md` 与本文或 `AtriumSteward/AGENTS.md` 不一致时：**只能扩写或收紧（更严格）**，不得静默改写；确需覆盖必须在条目开头标 `[MARK]`，写明覆盖了哪一条、理由与影响范围。规则与格式见 [`AGENT_ROLES.md`](AGENT_ROLES.md) §4。

### 6.3 需人工决策的事项

Agent 不得自行拍板：目录边界调整、跨仓库契约字段冻结、是否引入新的重型第三方依赖、是否新建仓库或工具立项。

### 6.4 变更禁区

| 类型 | 规则 |
| :-- | :-- |
| 第三方源码 | 原则上禁止直接修改；确需个性化时迁移到自有目录 |
| 生成文件 | 禁止手工修改，必须由脚本或生成流程重建 |
| 归档文档 | 禁止修改 |
| 设计文档 | 仅允许架构师角色修改 |
| 未决项 | 标注为 `pending`，不得擅自定案 |

## 7. 验证要求

工作区尚未形成统一的测试分层与性能约束清单。在此之前，每个仓库的 `AGENTS.md` 必须给出"改动前后需要执行或人工核对的最小检查项"。

**目前最低要求**：

1. 改动的仓库能构建或导入通过（干净执行，非增量）。
2. 涉及工具进程时，验证 `启动 → 就绪 → 收到 shutdown → 退出码 0`，并确认无孤儿进程。
3. 涉及接口或契约时，同步更新对应架构文档。

记为 `pending` 的事项：统一测试分层、性能基线、安全约束、各 `Projects/` 是否引入 `project_status.yaml`（**当前 7 个项目均无该文件，扫描能力也尚未实现**）。
